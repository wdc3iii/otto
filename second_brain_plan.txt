## 1. Goal

An **AI-native, plain-markdown** knowledge base that you (Claude Code) can read,
structure, link, and query — with Obsidian as the human-facing graph/browser.
Priorities, in order:

1. **Reading & synthesis** over generation. I think far more often than I
   produce artifacts — the highest-value use is you *reading* across my notes
   and surfacing non-obvious connections, not writing prose for me.
2. **Low maintenance.** Manual PKM systems die within weeks. The whole point is
   that the routine (filing, tagging, linking, indexing) is handled by you.
3. **No lock-in.** Everything stays as plain `.md` on disk, in git.

## 3. Phase 1 — Vault skeleton

Create this folder structure (tuned for research, not generic productivity).
Add a short `index.md` to each top-level folder describing what belongs there.

```
[VAULT_NAME]/
├── SECOND-BRAIN-SETUP.md   # this file (can be deleted after setup)
├── CLAUDE.md               # your standing instructions (Phase 2)
├── .claude/                # skills, settings — NOT authentic notes
├── 00-Inbox/               # raw capture, unsorted. Safe zone for you to edit freely.
├── 01-Projects/            # active outputs with a deadline/definition of done
│   ├── papers/             #   one folder per paper (drafts, notes, figures)
│   ├── talks/              #   one folder per talk
│   └── teaching/           #   per-course materials, problem sets, lectures
├── 02-Literature/
│   ├── papers/             # one note per paper, filename = citekey (e.g. ames2019cbf.md)
│   └── topics/             # Maps of Content (MOCs) / lit-review hubs per subfield
├── 03-Concepts/            # atomic evergreen notes (one idea each): CLFs, CBFs,
│                           #   HJB, PPO, teacher-student distillation, LIP, ...
├── 04-Resources/           # reference material, code snippets, configs, cheatsheets
├── 05-Archive/             # completed / inactive
├── Meetings/               # dated meeting notes (advisor, collaborators)
├── Journal/
│   ├── daily/              # daily notes
│   └── sessions/           # YOUR session logs — this is the memory layer
└── Templates/              # note templates (paper, concept, daily, meeting)
```

Notes on intent:
- **`02-Literature/papers/`** = per-source reading notes (bibliographic).
  **`03-Concepts/`** = distilled, source-independent, atomic notes. Keep these
  separate: reading notes cite sources; concept notes are my own crystallized
  understanding, densely `[[wikilinked]]`.
- **`02-Literature/topics/`** MOCs are the backbone of any lit review — a hub
  note per subfield that links out to the relevant paper + concept notes.

## 4. Phase 2 — CLAUDE.md

Create a `CLAUDE.md` at the vault root. Write it like you're **onboarding a new
research assistant on day one** — not like documentation. Use this as the
skeleton and fill it in with me:

```markdown
# CLAUDE.md — [VAULT_NAME]

## Who I am
[2–3 sentences: robotics researcher, humanoid locomotion + navigation autonomy,
control theory + RL, teaching, paper writing. Pull the relevant bits from
Section 0 of the setup brief.]

## What this vault is
My academic second brain. Reading notes, atomic concept notes, literature MOCs,
and project/talk/course work. Optimize for reading & synthesis over generation.

## Folder map
[One line per top-level folder describing what lives there and where you should
write new content. Link to each folder's index.md — "layered discovery".]

## Conventions
- Filenames: paper notes = citekey (e.g. `olkin2024dtmpc.md`); concept notes =
  kebab-case concept name.
- Every paper note links to the concepts it uses; every concept note links to
  the papers that ground it.
- Frontmatter on every note: `type`, `tags` (max 3, from existing taxonomy),
  `created`, and for papers `authors`, `year`, `venue`, `url`/`doi`.
- Prefer `[[wikilinks]]`. Keep links tight: only link A→B when understanding A
  genuinely changes how I see B.

## How to behave
- Default to **thinking mode**: ask me clarifying questions before generating.
- When ingesting a source, produce an atomic reading note + suggest concept
  links; don't dump a wall of text.
- Report what you changed at the end of every session (files created/moved,
  links added, anything that didn't fit the taxonomy).

## Hard rules (see Guardrails in the setup brief)
- Never delete notes. Never rewrite the *content* of existing notes without asking.
- Never rename/move heavily-linked notes at the OS level (breaks wikilinks).
- Keep your own plans/scratch out of the vault proper (use `.claude/`).

## Maintenance
- Whenever you create or delete a file, update that folder's `index.md`.
- At session start, read the two most recent logs in `Journal/sessions/`.
- At session end, write a new session log (see Phase 3).
```

**CHECKPOINT 2** — draft the filled-in CLAUDE.md, show it to me, iterate until

You have **no persistent memory** between sessions. We fake it with logs.

1. Create a session-log template in `Templates/session.md` with sections:
   `## Context (what I was doing)`, `## Changes made`, `## Open threads /

  tasks; surface active project priorities from `01-Projects/`.
- **`capture`** — take a raw dump (paste, link, transcript) from `00-Inbox/`,
  break it into atomic notes, file them, add frontmatter + wikilinks, report.
- **`weekly-review`** — read across areas and surface **non-obvious
  connections and contradictions** in my thinking. This is the payoff workflow.

## 8. Guardrails (apply throughout)

1. **Wikilinks are load-bearing and fragile.** You operate at the OS level;
   Obsidian only auto-relinks on renames done *inside the app*. Renaming or
   moving a `.md` at the filesystem level **silently breaks every `[[link]]`**
   pointing at it. So: freely reorganize `00-Inbox/` and new drafts, but
   **never rename/move a note that shows up heavily in the graph** without
   asking me first — and if I approve, fix the inbound links too.
2. **Don't pollute the vault with generated content.** My authentic thinking
   lives in the vault; your plans, scratch, and memory live in `.claude/` and
   `Journal/sessions/`.
3. **Capture before organizing.** Getting things *in* beats perfect filing.
4. **Never delete notes.** Never rewrite existing note *content* without asking.
5. **Constrain, don't sprawl.** Max 3 tags/note from the existing taxonomy;
   tight linking only. If the structure feels inadequate, tell me — propose an
   improvement rather than silently working around it.
6. **Everything in git.** Commit at logical checkpoints so mistakes are cheap.
